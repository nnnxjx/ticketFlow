# TicketFlow 首版交易规则（v1）

本文是实现与测试的依据。首版只支持**整单取消、整单退款**；一条订单明细对应一张票。无座订单只买一个场次的一个票档；选座订单只买一个场次的若干座位，不使用票档。真实支付和资金清算不在范围内。

步骤 4 先实现 MySQL 同步无座下单：直接以 `ticket_order(user_id,request_id)` 唯一键幂等，在同一事务中条件扣减库存、增加限购占用并写明细。下表中的 Redis 预占、`purchase_request`、outbox 和 MQ 流程属于后续异步优化阶段，启用时替换同步入口并补齐恢复机制。

## 1. 固定口径

| 主题 | 规则 |
| --- | --- |
| 场次模式 | `event_session.sale_mode` 决定整个场次的购票流程。`GENERAL` 按票档数量抢购，以 `ticket_tier.available_stock` 为权威库存；`ASSIGNED` 按具体座位购买，以 `session_seat.status` 为权威库存。选座场次不创建票档。 |
| 数量与价格 | 无座数量至少 1 张，受每用户累计限购及库存约束，价格来自票档；选座数量受平台单次上限约束，价格为各座位 `session_seat.price` 之和。不接受客户端价格。 |
| 限购 | 无座模式按用户、票档限购，数据库 `user_tier_quota.active_qty` 为最终约束；选座模式首版只限制每单座位数，不做跨订单累计限购。无座订单的 `PENDING_PAYMENT/PAID/TICKETED/REFUNDING` 占名额，`CANCELLED/REFUNDED` 不占。 |
| 销售窗口 | 场次满足 `event_session.sale_start <= NOW(3) < sale_end`，且状态可售；无座模式还需满足票档自身销售窗口。支付可在销售结束后继续，但必须在订单到期前。 |
| 锁定时长 | 创建订单时写入统一的 `expire_at`，建议 15 分钟。支付仅在 `NOW(3) < expire_at` 时成功；到期时由关单获胜。页面倒计时只作展示。 |
| 幂等 | 每次购票提交携带 `request_id`。同一用户同一 `request_id` 重试返回同一结果；相同键但请求内容不同返回冲突。支付、退款、检票也分别使用业务唯一键或条件状态转换。 |
| 退款后转售 | 模拟退款成功且仍在销售窗口、场次未开始时恢复可售；否则释放名额但不重新售卖。选座票转为 `FREE` 或 `UNAVAILABLE`；不选座票仅在可转售时增加 `available_stock`。 |
| 时间和金额 | 数据库存 UTC `DATETIME(3)`；API 使用 ISO 8601 带时区时间。金额为 `DECIMAL(12,2)` / `BigDecimal`，首版单币种 CNY。 |

## 2. 订单与票券状态

订单状态：`PENDING_PAYMENT -> PAID -> TICKETED`；`PENDING_PAYMENT -> CANCELLED`；`PAID/TICKETED -> REFUNDING -> REFUNDED`。退款失败从 `REFUNDING` 恢复原状态（在 `refund_record.previous_order_status` 中记录）。`TICKETED` 表示电子票已生成，检票结果以每张 `ticket` 为准，不因一张票入场而修改整单状态。

票券状态：`UNUSED -> USED`；`UNUSED -> REFUNDING -> INVALID`；退款失败 `REFUNDING -> UNUSED`。订单进入退款流程时，必须先把**所有**票券从 `UNUSED` 改为 `REFUNDING`；任一票券已 `USED` 则整单退款失败且事务回滚。

## 3. 交易操作表

| 操作 | 前提与竞争条件 | 同一数据库事务中的变化 | 重复/失败处理 |
| --- | --- | --- | --- |
| 不选座预占 | 请求指纹一致、销售窗口有效、Redis 库存和临时限购令牌充足 | 先持久化 `purchase_request(INIT)`；Lua 以请求 ID 原子预占并保存令牌；将请求标为 `RESERVED`，写 `outbox_event` | `INIT` 恢复任务查询 Redis 令牌后继续或重试。不能仅靠 Lua 返回值判断是否已经预占。 |
| 不选座建单 | 消费 `RESERVED` 请求；票档仍属于指定场次 | 条件扣减 `available_stock`；条件增加 `user_tier_quota.active_qty`；创建订单和逐张明细；请求标为 `ORDERED` | 按 `purchase_request.order_id` 与订单唯一键幂等。失败记录原因，确认未建单后释放 Redis 令牌。MQ 仅负责唤醒；定时扫描待处理请求兜底。 |
| 选座建单 | 所选座位均属于该场次、状态 `FREE`；数量满足平台单次上限 | 按座位 ID 排序条件更新为 `LOCKED` 并绑定订单；创建订单和逐张明细，价格取各座位之和；写超时任务 | 任一座位更新为 0 行则整笔事务回滚。重试按 `(user_id,request_id)` 返回原订单。 |
| 主动取消/超时关单 | 订单仍 `PENDING_PAYMENT`；超时关单额外要求 `expire_at <= NOW(3)` | 条件转 `CANCELLED`；释放该订单持有的座位或回补不选座库存；无座订单减少限购数量；写库存流水 | 状态转换 0 行时先读取当前状态，不再释放。座位释放必须同时匹配 `lock_order_id`。 |
| 模拟支付 | 订单归属正确，仍 `PENDING_PAYMENT` 且 `expire_at > NOW(3)` | 条件转 `PAID`；选座座位 `LOCKED -> SOLD`；写唯一支付流水及出票任务 | 与关单只能一个成功。重复支付返回已有支付结果，不重复修改座位。 |
| 出票 | 订单 `PAID`，明细完整 | 每张明细生成一张票，随机令牌只返回给持有人，库中保存哈希；全部完成后订单转 `TICKETED` | `ticket(order_item_id)` 唯一；重复任务只补缺少的票，不能覆盖已发令牌。令牌交付策略见下文。 |
| 检票 | 当前用户是该演出主办方的负责人、时间在检票窗口、票券 `UNUSED` | 条件转 `USED`，写唯一 `checkin_record` | 0 行返回已用/退款中/作废等结果；不能再次记成功。 |
| 申请整单退款 | 订单 `PAID/TICKETED`，未过退款截止时间；所有票券均 `UNUSED`（`PAID` 未出票时允许无票） | 创建唯一退款申请；订单转 `REFUNDING`；已有票券全部转 `REFUNDING` | 同一订单同一轮退款返回原申请；检票与退款通过票券条件更新竞争。 |
| 模拟退款完成 | 退款申请 `PROCESSING`、订单 `REFUNDING` | 退款转 `SUCCEEDED`；票券转 `INVALID`；订单转 `REFUNDED`；减少限购；根据可转售条件恢复库存或座位；写唯一库存流水 | 退款完成事件重放不会重复回补。失败则恢复订单原状态及票券 `UNUSED`。 |

## 4. 关键一致性约定

1. Redis 预占与 MySQL/MQ 无分布式事务。`purchase_request` 在 Lua 前落库；Lua 将请求 ID、数量、过期时间作为幂等令牌保存。恢复程序扫描 `INIT/RESERVED`，查询令牌、订单及 outbox 状态，决定补发或释放。释放 Lua 必须按请求 ID 执行一次。令牌 TTL 要覆盖下单处理及恢复窗口；过期前未收敛时暂停该票档销售并按数据库对账，不能无条件重置库存。
2. `outbox_event` 与请求状态在同一 MySQL 事务提交。发布器扫描未确认事件，发送 RabbitMQ 并记录确认；消费者按业务 ID 幂等。消息可能重复，不能假设恰好投递一次。
3. 选座订单的锁座和订单创建在一个事务；支付、关单和退款分别用订单状态条件更新抢占转换权。所有批量座位更新按 ID 排序，检查影响行数等于明细数。`ticket_order_item.session_seat_id` 只建普通索引：退款后允许同一座位再次出售，历史明细仍须保留；同一时刻的独占由 `session_seat.status` 条件更新保证。
7. `ticket_order.sale_mode` 是下单时的场次模式快照。创建订单时从 `event_session.sale_mode` 复制，不接受客户端直接指定；已开售场次不允许切换模式。
4. 出票令牌不能只保存不可逆哈希后就丢弃原值，否则用户再次打开电子票无法展示二维码。建议票券另存**加密后的令牌密文**供授权用户读取，哈希用于检票查找；加密密钥放环境变量并支持轮换。日志、URL、统计接口不得暴露原令牌。
5. 发布后限制修改场次模式、票档价格、座位价格及座位映射。改价应在未产生订单时进行；无座模式也可新建票档。订单明细保存票档名称或座位位置与价格快照。
6. 所有跨表归属（场次属于演出、座位属于场次、演出属于当前用户负责的主办方）在服务层事务中校验；DDL 的单列外键无法完全表达这些关系。

## 5. 必须验证的边界

- 同一请求重试与相同请求 ID 不同参数；Redis 预占后进程崩溃；outbox 发布后确认丢失；消费者提交后 ACK 丢失。
- 支付与主动取消/超时关单竞争；超时消息延迟到新订单锁座后才到达；多座位其中一个已占。
- 两台设备同时检票；检票与退款同时发生；退款完成事件重复；退款后过了销售截止时间。
- 同一用户并发创建多个订单，合计超过限购；选座和不选座模式的库存均不超卖。
