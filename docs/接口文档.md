# TicketFlow API

后端启动后访问：

- Swagger UI：`http://127.0.0.1:8080/swagger-ui.html`
- OpenAPI JSON：`http://127.0.0.1:8080/v3/api-docs`
- 健康检查：`http://127.0.0.1:8080/actuator/health`

所有业务接口使用 `/api/v1` 前缀。成功响应结构为 `code/message/data/requestId`，响应头也包含 `X-Request-Id`。受保护接口由 Spring MVC `AuthInterceptor` 校验登录态；在 Swagger 的 **Authorize** 中填入登录返回的原始 JWT，实际请求头为 `Authorization: <token>`，不加 `Bearer`。主办方数据归属由 Service 继续校验。

API 中的 `BIGINT` ID 以 JSON 字符串返回，前端提交 ID 时也使用字符串，避免 JavaScript 对雪花 ID 做整数舍入。数量和金额仍按数值处理。

| 方法 | 路径 | 鉴权 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/api/v1/auth/register` | 否 | 手机号与密码注册；密码至少 8 位 |
| `POST` | `/api/v1/auth/login` | 否 | 登录并获取 JWT；本地 `dev` 配置下暂不过期 |
| `GET` | `/api/v1/auth/me` | 是 | 获取当前账号 |
| `POST` | `/api/v1/organizers` | 是 | 创建主办方，当前账号成为负责人；每账号限一个 |
| `GET` | `/api/v1/organizers/me` | 是 | 获取当前账号负责的主办方 |
| `GET` | `/api/v1/system/ping` | 否 | 基础连通性检查 |

注册示例：

```json
{"phone":"13800138000","password":"examplePassword123"}
```

登录示例：

```json
{"phone":"13800138000","password":"examplePassword123"}
```

创建主办方示例：

```json
{"name":"城市音乐节主办方"}
```

本地 `dev` 配置的 JWT 暂不过期，仅用于测试；其他环境默认 2 小时过期。当前 JWT 无服务端撤销列表。“退出登录”由客户端删除令牌实现；禁用账号后，后端会在后续请求中拒绝其令牌。真实上线前还应补充登录限流、令牌撤销/刷新策略及更完整的审计能力。

## 演出与商品管理

下列管理接口均需要原始 JWT；后端根据当前登录用户查找其唯一的主办方，无需在路径中传主办方 ID。越权资源返回 404。草稿场次删除时在同一事务删除关联票档或场次座位；已有订单的场次不可删除。开售后不能随意修改价格、容量、场次模式或座位映射。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST/GET` | `/api/v1/organizer/events` | 创建/列出当前主办方演出 |

| `POST` | `/api/v1/organizer/events/{id}/publish` | 发布演出，要求至少一个已启用场次 |
| `POST` | `/api/v1/organizer/events/{id}/off-shelf` | 下架演出 |

| `POST` | `/api/v1/organizer/sessions/{id}/activate` | 启用场次；无座需有已启用票档，选座需已初始化座位 |

## 公开查询

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/v1/events` | 已发布演出列表 |
| `GET` | `/api/v1/events/{id}` | 已发布演出详情 |
| `GET` | `/api/v1/events/{eventId}/sessions` | 已启用场次 |

| `GET` | `/api/v1/sessions/{sessionId}/seats` | 选座场次座位与价格 |
| `GET` | `/api/v1/sessions/{sessionId}/seats/stream` | 公开 SSE 座位变化通知，事件包含场次 ID、座位 ID、版本；建立连接或重连后重新读取座位快照 |

场次时间以 UTC 的 `yyyy-MM-ddTHH:mm:ss` 格式传入。所有场次都必须选择场馆；选座场次还需要先建立场馆座位模板。建议先创建场馆，再创建演出与场次、配置票档或场次座位、启用票档/场次，最后发布演出。

无座场次请求示例：

```json
{"venueId":1001,"saleMode":"GENERAL","saleStart":"2027-01-01T09:00:00","saleEnd":"2027-01-05T18:00:00","startTime":"2027-01-06T19:00:00","endTime":"2027-01-06T22:00:00","checkinStart":"2027-01-06T17:00:00","checkinEnd":"2027-01-06T21:00:00"}
```

无座票档请求示例：

```json
{"name":"VIP","price":1280.00,"totalStock":500,"perUserLimit":4,"saleStart":"2027-01-01T09:00:00","saleEnd":"2027-01-05T18:00:00"}
```

选座场次将 `saleMode` 改为 `ASSIGNED`；此模式不创建票档。场次草稿在初始化座位后可逐座改价，再启用场次。

## 无座票下单与我的订单（步骤 8）

以下接口均需在 `Authorization` 请求头传原始 JWT。`requestId` 由客户端为每次购票操作生成；只有用户再次提交同一次操作时才复用。相同账号、相同 `requestId` 和参数会返回原请求状态，参数不同返回 `REQUEST_ID_CONFLICT`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/v1/orders/general` | 异步受理无座票下单；仅接受票档 ID、数量和请求 ID，返回请求状态 |
| `POST` | `/api/v1/orders/assigned` | 同步选座下单；提交场次 ID、座位 ID 列表和请求 ID，全部锁座成功才返回订单 |
| `GET` | `/api/v1/orders/general/async/{requestId}` | 按当前用户的 `requestId` 从 Redis 轮询异步下单状态；未找到返回 `UNKNOWN`，不回查数据库 |
| `GET` | `/api/v1/orders/{id}` | 查看本人订单和逐张票价快照；其他用户订单返回 404 |
| `GET` | `/api/v1/orders?page=1&size=20` | 分页列出本人订单；`size` 不超过 100，列表不包含明细 |
| `POST` | `/api/v1/orders/{id}/cancel` | 取消本人待支付订单；重复取消返回已取消订单 |
| `POST` | `/api/v1/orders/{id}/pay` | 模拟支付本人未到期的待支付订单；重复支付返回原支付流水 |
| `GET` | `/api/v1/orders/{id}/tickets` | 查看本人已出票订单的票券和令牌；可由前端将令牌渲染为二维码 |
| `POST` | `/api/v1/organizer/checkins` | 主办方负责人检票；请求体 `{"token":"..."}` |
| `POST` | `/api/v1/orders/{id}/refund` | 申请本人订单整单模拟退款；仅 `PAID/TICKETED` 且未过退款截止时间 |
| `GET` | `/api/v1/orders/{id}/refund` | 查询本人订单最近一次退款的状态 |
| `POST` | `/api/v1/orders/{id}/refund/simulate-failure` | 仅 `dev` 环境：模拟本人退款失败并恢复订单和票券 |

```json
{"requestId":"buy-20270101-001","tierId":1002,"quantity":2}
```

选座下单示例：

```json
{"requestId":"seat-20270101-001","sessionId":2001,"seatIds":[3001,3002]}
```

选座场次先由主办方建立场馆物理座位模板，初始化场次座位并按需改价。`GET /api/v1/sessions/{sessionId}/seats` 返回每座的区域、排号、座号、价格、状态及 `version`；该快照只供展示。选座订单一次最多 8 座（`ticketflow.order.max-seats-per-order` 可配置），不能重复提交同一座位 ID。服务端按 ID 顺序条件锁定 `FREE` 座位，并以数据库价格合计订单金额；任一座位被占用则整单回滚，返回 `SEAT_UNAVAILABLE`。订单明细返回 `sessionSeatId` 和位置、价格快照。相同 `requestId` 和同一组座位返回原订单，参数不同返回 `REQUEST_ID_CONFLICT`。付款后座位转 `SOLD`；取消或超时关单只释放仍归本单所有的锁座，仍可售时转 `FREE`，否则转 `UNAVAILABLE`。整单模拟退款采用相同可转售判断。已建库需先执行[选座位置快照长度迁移](./已建库_选座位置快照长度.sql)。

订单创建成功后状态为 `PENDING_PAYMENT`，默认 15 分钟后到期；数量至少 1 张，受票档的每用户累计限购及库存约束，不设单独的每单上限。库存不足返回 `SOLD_OUT`，累计限购超出返回 `LIMIT_EXCEEDED`。后台每 30 秒扫描到期订单；取消或超时关单在同一 MySQL 事务内释放限购，只有演出、场次、票档仍可售且在销售窗口、场次未开始时才恢复无座可售库存；事务提交后按同一结果回补 Redis。支付成功生成唯一模拟支付流水；出票任务默认每 5 秒扫描已支付订单，在事务内为每条明细补齐一张票并把订单转为 `TICKETED`。检票以数据库中的 `UNUSED` 条件更新为准，重复检票失败。票券令牌只在授权持有人查询电子票时返回，不应写入日志或 URL。

下单响应包含 `requestId`、`status`、`orderId`（仅 `ORDERED` 时有值）和 `failureCode`。`PROCESSING` 表示 Redis 已预占、订单尚未查到；`ORDERED` 表示订单创建成功；`REJECTED` 表示业务拒单；`UNKNOWN` 表示未查到此请求。发布确认超时仍返回 `PROCESSING`，客户端应使用相同 `requestId` 和参数重试。成功后使用订单详情接口获取金额和支付截止时间。草稿票档可以反复编辑；首次启用读取最终库存并初始化 Redis，已停售票档重新启用时保留原 Redis 库存。旧库若已有 `purchase_request` 和 `outbox_event`，确认数据无需保留并备份后，可执行[移除旧表脚本](./已建库_移除异步请求与Outbox表.sql)；如果此前添加过 `order_channel` 字段，再执行[移除票档通道字段脚本](./已建库_移除票档通道字段.sql)。

本地开发的票券密钥放在 Git 忽略的 `backend/src/main/resources/application-local.yml`，Spring 会可选加载。其他环境通过 `TICKET_ENCRYPTION_KEY` 提供 32 字节密钥的 Base64；换密钥时可改用 `TICKET_ENCRYPTION_KEYS`（如 `1:<旧密钥>,2:<新密钥>`）并设置 `TICKET_ACTIVE_KEY_VERSION=2`。历史版本密钥需保留至对应票券不再需要展示。

整单退款默认截止于场次开始前 24 小时。申请后订单与尚未使用的电子票进入 `REFUNDING`；任一票已检票则整单拒绝。后台每 5 秒扫描待处理申请并模拟退款成功：票券转 `INVALID`、订单转 `REFUNDED`；无座订单释放每用户限购，仅活动和票档仍可售且处于销售窗口、场次未开始时回补库存；选座订单仅在演出和场次仍可售且处于销售窗口、场次未开始时把原订单的座位转 `FREE`，否则转 `UNAVAILABLE`。重复请求返回现有退款结果。开发环境可用模拟失败接口演示 `REFUNDING -> PAID/TICKETED` 和票券恢复；若后台已先结算成功，该接口仅返回已完成的结果。

### 请求体字段

表中未标“可选”的字段均为必填。`datetime` 是 UTC `yyyy-MM-ddTHH:mm:ss` 字符串；`decimal` 是 JSON 数值，最多两位小数。`seatIds` 是 ID 字符串数组。

| 请求体 | 字段与格式 |
| --- | --- |
| `RegisterRequest` | `phone:string`（手机号）、`password:string`（至少 8 位） |
| `LoginRequest` | `phone:string`、`password:string` |
| `CreateOrganizerRequest` | `name:string`（非空） |
| `EventRequest` | `title:string`（最多 200 字符）；`category:string`（可选，最多 64）；`description:string`（可选） |
| `VenueRequest` | `name:string`（最多 128）；`address:string`（可选，最多 255） |
| `VenueSeatRequest` | `area:string`（最多 64）、`rowNo:string`（最多 32）、`seatNo:string`（最多 32） |
| `SessionRequest` | `venueId:ID`、`saleMode:"GENERAL"\|"ASSIGNED"`、`saleStart:datetime`、`saleEnd:datetime`、`startTime:datetime`、`endTime:datetime`、`checkinStart:datetime`、`checkinEnd:datetime` |
| `TierRequest` | `name:string`（最多 80）、`price:decimal`（≥0）、`totalStock:int`（≥0）、`perUserLimit:int`（≥1）、`saleStart:datetime`、`saleEnd:datetime` |
| `SeatPriceRequest` | `price:decimal`（≥0） |
| `CreateGeneralOrderRequest` | `requestId:string`（非空，最多 64）、`tierId:ID`、`quantity:int`（≥1） |

### 成功返回的 `data` 字段

所有 `ID` 字段在 JSON 中是字符串；`ID?` 表示可为 `null`。金额为 JSON 数值，时间为 UTC 字符串。`OrderPageView.orders` 中的 `OrderView.items` 是空数组，详情接口才返回逐张明细。

| `UserView` | `id:ID, phone:string, status:string` |
| `LoginView` | `accessToken:string, tokenType:string, expiresInSeconds:int, user:UserView` |
| `OrganizerView` | `id:ID, name:string, status:string` |
| `EventView` | `id:ID, organizerId:ID, title:string, category:string?, description:string?, status:string` |

SSE 每次座位变化发送 `data: {"sessionId":"...","seatId":"...","version":"..."}`；连接建立时可能先收到 `:connected` 注释。SSE 不保证补发历史事件，连接或重连后应重新查询座位列表。

例如异步下单成功受理时的完整 HTTP 响应体：

```json
{"code":"OK","message":"success","data":{"requestId":"buy-001","status":"PROCESSING","orderId":null,"failureCode":null},"requestId":"http-trace-001"}
```

轮询建单完成后：

```json
{"code":"OK","message":"success","data":{"requestId":"buy-001","status":"ORDERED","orderId":"1234567890123456789","failureCode":null},"requestId":"http-trace-002"}
```

`data.requestId` 是购票幂等键，顶层 `requestId` 是这次 HTTP 请求的追踪号。两次轮询的追踪号可能不同。订单详情、支付、退款等响应将上述 `data` 对象替换为表中对应的 View 字段。
