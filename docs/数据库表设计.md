# TicketFlow 数据库表设计说明（首版）

配套文件：[建表脚本](./schema.sql) · [交易规则](./交易规则.md)。目标数据库为 MySQL 8.0.16 及以上版本；本机安装的 MySQL 8.4 满足版本要求。所有业务时间按 UTC 存储为 `DATETIME(3)`，应用连接也应使用 UTC。

## 1. 总体约定

- 主键 `id` 为应用生成的 `BIGINT`，建表脚本没有 `AUTO_INCREMENT`。
- 金额使用 `DECIMAL(12,2)`，币种在首版固定为人民币；Java 使用 `BigDecimal`。
- `created_at`、`updated_at` 记录创建和更新时间。状态字段只允许交易规则中列出的转换，数据库 `CHECK` 只限制取值，不能替代转换检查。
- 脚本**没有声明外键**。跨表归属由服务层在事务中校验；删除业务数据建议软删除或停用，不要物理删除有订单引用的记录。缺少外键意味着导入数据、管理脚本也必须遵守这些规则。
- `event_session.sale_mode` 决定整个场次的购票流程。`GENERAL` 场次按票档数量抢购，以 `ticket_tier.available_stock` 为库存；`ASSIGNED` 场次按具体座位购买，以 `session_seat.status` 为库存，不创建 `ticket_tier`。
- 一笔订单仅属于一个场次；无座订单关联一个票档，选座订单关联若干座位。一条 `ticket_order_item` 对应一张票。首版仅支持整单取消、整单退款。

## 2. 表清单

| 表 | 用途 | 关键字段 | 关键约束或索引 |
| --- | --- | --- | --- |
| `users` | 购票用户和主办方负责人账号 | `phone`, `password_hash`, `status` | 手机号唯一 |
| `organizer` | 主办方主体 | `owner_user_id`, `name`, `status` | `owner_user_id` 唯一：每个账号至多负责一个主办方 |
| `venue` | 场馆 | `organizer_id`, `name`, `address` | 按主办方查询 |
| `venue_seat` | 场馆物理座位模板 | `venue_id`, `area`, `row_no`, `seat_no` | `(venue_id,area,row_no,seat_no)` 唯一；不同区域可以从同一排、同一座号重新编号 |
| `event` | 演出信息 | `organizer_id`, `title`, `status` | 按主办方、状态及发布时间查询 |
| `event_session` | 演出的具体场次及购票模式 | `event_id`, 必填 `venue_id`, `sale_mode`, `sale_start`, `sale_end`, `start_time`, `end_time`, 检票窗口 | 模式为 `GENERAL/ASSIGNED`；任何场次都要明确演出场馆 |
| `ticket_tier` | 场次内票档、定价与销售设置 | `session_id`, `price`, `total_stock`, `available_stock`, `per_user_limit` | 场次内名称唯一；每用户累计限购；票档购票统一异步受理 |
| `session_seat` | 场次独立的座位价格与状态 | `session_id`, `venue_seat_id`, `price`, `status`, `lock_order_id`, `lock_expire_at`, `version` | `(session_id,venue_seat_id)` 唯一；按场次状态及锁定订单查询 |
| `user_tier_quota` | 用户在票档内已占用的限购数量 | `user_id`, `tier_id`, `active_qty` | `(user_id,tier_id)` 主键；数量非负 |
| `ticket_order` | 订单主表 | `user_id`, `session_id`, 可空 `tier_id`, `amount`, `status`, `expire_at` | `(user_id,request_id)` 唯一；选座订单的 `tier_id` 为空 |
| `ticket_order_item` | 每张票的购买明细 | `order_id`, 可空 `tier_id`, 可空 `session_seat_id`, `item_name_snapshot`, `price_snapshot` | 票档或座位二选一；座位 ID **不唯一**，允许退款后再售并保留历史 |
| `payment_record` | 模拟支付成功流水 | `order_id`, `payment_no`, `amount`, `paid_at` | 订单和支付流水号分别唯一 |
| `ticket` | 电子票与检票凭证 | `order_item_id`, `token_hash`, `token_ciphertext`, `status` | 明细与令牌哈希分别唯一 |
| `checkin_record` | 成功检票记录 | `ticket_id`, `operator_id`, `checked_at` | 一张票最多一条成功检票记录 |
| `refund_record` | 整单模拟退款申请及处理结果 | `order_id`, `refund_no`, `previous_order_status`, `status` | 退款流水号唯一；按订单和状态查找 |
| `inventory_log` | 库存和座位变化的幂等流水 | `operation_id`, `order_id`, 可空 `tier_id/session_seat_id`, `operation`, `quantity` | 票档或座位二选一；业务操作 ID 唯一 |

## 3. 主要关系与校验

```text
organizer ── event ── event_session ── ticket_tier
     │                       │                │
     └── venue ── venue_seat ── session_seat  │
users ── ticket_order ── ticket_order_item ── ticket
              │                 │                 └── checkin_record
              ├── payment_record
              ├── refund_record
              └── inventory_log
users + ticket_tier ── user_tier_quota
```

应用必须校验：无座订单的 `ticket_tier.session_id = ticket_order.session_id`；选座订单的 `tier_id` 为空，且所有 `session_seat.session_id` 均匹配订单；`venue_seat.venue_id = event_session.venue_id`。主办方后台接口须通过演出所属 `organizer.owner_user_id` 与当前登录用户比对。DDL 的单字段和普通索引不保证这些跨表关系。

## 4. 关键字段解释

### 库存、限购和座位

- `ticket_tier` 只用于 `GENERAL` 场次，`total_stock` 是配置容量，`available_stock` 在订单创建时减；取消或退款完成时，仅仍符合转售条件才加。`ASSIGNED` 场次直接为每个 `session_seat` 配置价格。
- `user_tier_quota.active_qty` 只用于无座场次，统计待支付、已支付、已出票、退款中的票数。创建订单时条件增加，取消或退款完成时减少。选座场次首版仅限制单次数量。
- `session_seat.status` 为 `FREE/LOCKED/SOLD/UNAVAILABLE`。锁座时写 `lock_order_id` 和 `lock_expire_at`；支付后转 `SOLD` 并清空过期时间，保留订单 ID 便于退款校验；取消或退款时仅在仍可转售时转 `FREE`，否则转 `UNAVAILABLE`，均清空归属和过期时间。`version` 每次状态改变递增，供座位图忽略旧事件。

### 请求与订单

- 票档购票只开放异步入口。请求在 Redis 中以用户 ID 和 `requestId` 保存票档 ID、数量的预占令牌；相同参数重试复用令牌并可重发 MQ，参数不同返回冲突。订单写入后，`ticket_order(user_id,request_id)` 唯一键防止重复消息重复建单。
- `ticket_order.amount` 与 `quantity`、每条明细价格快照必须在事务中一致。客户端传入的金额不可信。
- `ticket_order.expire_at` 是服务端关单和支付竞争的判定时间。支付与取消都通过带当前状态条件的 `UPDATE` 争取转换权。

### 票券与异步任务

- `ticket.token_hash` 用于检票查找；`token_ciphertext` 用于授权用户再次打开二维码。加密密钥不能存入数据库或代码仓库。
- RabbitMQ 使用持久化 Direct Exchange 和一条持久化订单队列。请求线程在 Redis 预占成功后直接投递订单消息，并等待最多 5 秒的发布确认；确认超时或发送异常时保留预占，客户端可用相同 `requestId` 重试。消费者创建订单后确认 Redis 令牌；业务拒单则用 Lua 释放。消息重复投递由 MySQL 订单唯一键和 Redis 标记处理。
- Redis 预占令牌没有自动过期时间，避免消息延迟处理时库存被提前释放。没有预请求表、Outbox 或恢复扫描：预占后进程中断且客户端不重试，或者 MySQL 提交后 Redis 操作失败，都可能留下待人工对账的缓存差异。取消和退款先提交 MySQL，再直接回补 Redis；回补失败时记录错误，运维需核对库存与限购。不要未经对账用数据库库存覆盖 Redis。多实例运行时需为每个实例配置不同的 `TICKETFLOW_WORKER_ID`（0–1023）。
- 草稿票档无法售卖，可以修改价格与库存。启用票档时，在一个 MySQL 事务里按“场次行 → 票档行”的顺序加锁，读取最终库存配置，初始化 Redis，然后将状态更新为 `ON_SALE`。编辑和删除草稿票档也锁定票档行，条件更新要求状态仍为 `DRAFT`。若 Redis 初始化失败，数据库事务回滚；若 Redis 已初始化而事务提交失败，下次启用会在草稿状态下用最新数据库库存覆盖上次失败留下的缓存键。已开售的旧票档若尚无 Redis 库存键，需要停服核对库存和限购后初始化，不能直接把 Redis 库存设成总量。
- `inventory_log.operation_id` 推荐由 `操作类型 + 订单 ID` 形成稳定值，例如 `ORDER_RELEASE:12345`；重复任务复用同一值。

## 5. 执行与检查

脚本会创建 `ticketflow` 数据库及全部 16 张表。建议在**空数据库**执行一次；脚本不是迁移脚本，重复执行会因表已存在而报错。执行前确认连接的是预期的 MySQL 实例。

如果已执行旧版脚本，不能直接重跑建表脚本。**确认所有业务表都没有数据**后：若 `sale_mode` 还在 `ticket_tier`，先执行[购票模式调整](./已建库_购票模式调整.sql)，再执行[选座去票档调整](./已建库_选座去票档调整.sql)；若 `sale_mode` 已在 `event_session`，只执行后者。有业务数据时应先制定数据迁移方案。

若旧版数据库还有 `organizer_member` 表，确认其中没有需要保留的数据后，可执行[移除员工表脚本](./已建库_移除员工表.sql)。若数据库已按上一版结构运行，还需核对一人多主办方和无场馆场次，处理后执行[单主办方与场馆必填调整](./已建库_单主办方与场馆必填.sql)。已有 `ticket_tier.per_order_limit` 列的数据库需执行[移除单次限购脚本](./已建库_移除单次限购.sql)。

执行后可检查：

```sql
USE ticketflow;
SHOW TABLES;
SELECT COUNT(*) AS table_count
FROM information_schema.tables
WHERE table_schema = 'ticketflow';
SHOW CREATE TABLE ticket_order;
SHOW CREATE TABLE session_seat;
```

`table_count` 应为 `16`。若执行失败，请保留**第一条报错及 MySQL 版本**；不要在已经部分建表的库上反复运行整份脚本。

## 6. 建库后的开发顺序

1. 建立 Spring Boot 工程、数据库连接与迁移工具（建议 Flyway）；把当前 DDL 作为基线迁移，后续结构变化使用新迁移文件。
2. 先做用户登录与主办方负责人归属校验，以及演出、场次、票档的创建和查询；加入开发环境演示数据。
3. 实现**不依赖 Redis/MQ 的同步下单**：MySQL 条件扣库存、限购计数、订单及明细同事务创建，随后完成关单、模拟支付和出票。
4. 实现检票、整单退款和关键并发测试；确认基本交易闭环正确。
5. 再加入 Redis 预占和 RabbitMQ 异步下单，验证重复投递及失败释放；已有旧异步表且数据不需保留时，先备份再执行[移除旧表脚本](./已建库_移除异步请求与Outbox表.sql)。
6. 最后实现指定座位、座位图实时刷新、主办方统计和压测。这个顺序让库存与状态机先在单数据库事务中稳定，再增加异步链路。
