# TicketFlow 核心链路说明

本文描述当前实现；交易状态规则以[交易规则](./交易规则.md)为准，接口字段见[接口文档](./接口文档.md)。代码片段摘自 `backend/src/main/java` 和 `backend/src/main/resources/redis`，用于说明关键条件；完整异常处理、日志及对象构造请以源码为准。

## 1. 无座票异步下单

入口为 `POST /api/v1/orders/general`，请求体含 `requestId`、`tierId`、`quantity`。`requestId` 是客户端对**一次购票操作**生成的幂等键；同一用户重试必须复用它和原参数。它与 HTTP `X-Request-Id` 追踪号无关。

### 1.1 请求线程：查询、预占、发布

`OrderController.createGeneralAsync` 只把请求交给 `AsyncOrderServiceImpl.submit`。后者先查已有 MySQL 订单，再看 Redis 是否已有同参数令牌，避免重试重复扣减。新请求还要验证演出、场次和票档均可售。核心顺序为：

```java
OrderEntity existing = findOrder(userId, requestId);
if (existing != null) return ordered(existing, input.getTierId(), input.getQuantity());
boolean retry = stockGate.matchesToken(userId, requestId, input.getTierId(), input.getQuantity());
if (!retry && stockGate.hasToken(userId, requestId)) throw requestConflict();
TierEntity tier = retry ? tiers.getById(input.getTierId()) : purchasable(input.getTierId());
long result = stockGate.reserve(userId, requestId, tier, input.getQuantity());
```

Redis 的 `reserve.lua` 在一次 Lua 执行中判断库存和用户限购，并写入令牌；相同参数的重试返回 `2`，不再次扣库存：

```lua
local previous = redis.call('GET', KEYS[3])
if previous then
  if previous == value then return 2 end
  return -6
end
if tonumber(redis.call('GET', KEYS[1])) < qty then return -1 end
if tonumber(redis.call('GET', KEYS[2]) or '0') + qty > tonumber(ARGV[2]) then return -2 end
redis.call('DECRBY', KEYS[1], qty)
redis.call('INCRBY', KEYS[2], qty)
redis.call('SET', KEYS[3], value)
```

当前令牌**没有自动过期时间**，直到消费者确认建单或拒单释放。预占成功后，`submit` 直接向 RabbitMQ 发消息，并最多等待 5 秒发布确认。确认成功只能说明 broker 接收，不等于 MySQL 已建单。确认失败或超时也不能证明消息没有送达：

```java
if (!publish(body, userId, requestId)) {
    OrderEntity completed = findOrder(userId, requestId);
    if (completed != null) return ordered(completed, tier.getId(), input.getQuantity());
    log.warn("Order publish unconfirmed; retry with the same requestId: {}", requestId);
}
return new AsyncOrderView(requestId, "PROCESSING", null, null);
```

因此 `PROCESSING` 只表示 Redis 已预占、当前尚未查到订单。客户端轮询 `GET /api/v1/orders/general/async/{requestId}`；若长期处理中，按原 `requestId` 和参数重发 `POST`，复用令牌并重新投递 MQ。当前实现没有 `purchase_request`、outbox 或后台自动补发预占请求；只轮询而不重发，发布失败的请求可能一直处于 `PROCESSING`。不能把该状态展示为下单成功。

### 1.2 消费线程：MySQL 最终建单

消费者解析消息后调用 `AsyncOrderServiceImpl.consume`。它先查同用户同请求键的订单；若已存在则校验参数并确认 Redis 令牌，重复 MQ 消息不会再建单。没有订单时，必须有同参数 Redis 令牌才继续：

```java
if (!stockGate.matchesToken(userId, requestId, tierId, quantity)) return;
long orderId = orders.createAsync(userId, requestId, tierId, quantity);
stockGate.confirm(userId, requestId, tierId);
```

`OrderServiceImpl.createAsync` 在 MySQL 事务中执行 `writeOrder`。订单的 `(user_id,request_id)` 唯一键兜住并发重复消息；票档价格由数据库读取，订单和逐张明细、限购占用、数据库库存扣减同事务提交。Redis 只是入口预占，MySQL 条件更新仍作最终判断：

```java
quotas.reserve(userId, tier.getId(), quantity, tier.getPerUserLimit());
if (!tiers.update(new LambdaUpdateWrapper<TierEntity>()
        .eq(TierEntity::getId, tier.getId()).eq(TierEntity::getStatus, "ON_SALE")
        .ge(TierEntity::getAvailableStock, quantity)
        .setSql("available_stock = available_stock - {0}", quantity))) {
    throw new AppException(HttpStatus.CONFLICT, "SOLD_OUT", "票档库存不足或已停售");
}
```

订单写入后状态为 `PENDING_PAYMENT`，默认 15 分钟内支付。消费者确认令牌时不回补 Redis；若 MySQL 业务拒单，则释放 Redis 预占并记录失败。查询接口先查 MySQL 订单，找到返回 `ORDERED` 和 `orderId`；否则根据 Redis 失败标记、令牌或释放标记返回 `REJECTED`、`PROCESSING` 或 `UNKNOWN`。

## 2. 选座同步下单与座位变化

`POST /api/v1/orders/assigned` 直接返回 `OrderView`。服务端先验证座位 ID 列表，按当前用户与 `requestId` 查重；新订单在一个 MySQL 事务中创建。`writeAssignedOrder` 先锁定场次行，使停售与锁座不交错，然后核对选座模式、销售窗口、座位归属与数量。逐座按 ID 顺序把 `FREE` 条件更新为 `LOCKED` 并绑定本订单；任何一个座位更新不到行，整个事务回滚，已锁的座位也恢复。金额是各座位数据库价格之和，明细保存座位与价格快照。

```java
SessionEntity session = sessions.getOne(new LambdaQueryWrapper<SessionEntity>()
        .eq(SessionEntity::getId, sessionId).last("FOR UPDATE"));
```

座位变化只在事务提交后通过 `SeatEventPublisher` 向 SSE 连接广播：

```java
if (TransactionSynchronizationManager.isActualTransactionActive()) {
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() { send(sessionId, seatId, version); }
    });
}
```

客户端收到 `{sessionId,seatId,version}` 后重新获取座位快照；SSE 不承诺历史事件补发。

## 3. 支付、超时关单与库存释放

用户调用 `POST /api/v1/orders/{id}/pay` 进行模拟支付。`OrderServiceImpl.payPending` 在事务中以订单归属、`PENDING_PAYMENT` 状态和未到期条件争取状态转换；成功时记录唯一支付流水，选座座位转 `SOLD`。重复支付读取原支付结果。关单任务周期扫描到期订单，主动取消也调用 `cancelPending`；支付与关单只有一个能从 `PENDING_PAYMENT` 转走：

```java
if (!"PENDING_PAYMENT".equals(order.getStatus())) {
    if (expiredOnly || "CANCELLED".equals(order.getStatus())) return false;
    throw CatalogAccess.conflict("只有待支付订单可以取消");
}
```

取消无座订单时，MySQL 事务释放限购名额，并且只在仍可转售时恢复数据库可售库存；选座订单只释放仍由本订单持有的座位。事务提交后才调用 Redis 幂等回补。Redis 回补失败不会撤销已经提交的 MySQL 取消状态，相关票档需要对账。出票任务扫描已支付订单，为每条明细补齐电子票后把订单变为 `TICKETED`。

## 4. 整单退款与检票

`POST /api/v1/orders/{orderId}/refund` 校验订单归属、状态及退款截止时间。申请事务把订单和全部未使用票券转为 `REFUNDING` 并写退款流水；任一票已使用则整单失败。后台任务扫描 `PROCESSING` 退款，`RefundServiceImpl.settleOne` 在事务中把票券转 `INVALID`、订单转 `REFUNDED`，并按当前是否可转售决定释放限购、回补库存或座位。无座 Redis 回补在 MySQL 事务提交后执行：

```java
if (Boolean.TRUE.equals(transactions.execute(status -> settleOne(refund.getId())))) {
    completed++;
    creditSettledRefund(refund.getId());
}
```

主办方检票入口只接受票券令牌。`TicketServiceImpl.checkinOne` 先按令牌哈希查票，再校验所属主办方、检票窗口和票券状态；最终以 `UNUSED -> USED` 条件更新并写成功检票记录，重复检票不能再次成功。接口返回 `CheckinView`，不会返回原始令牌。
